Start3 of 3

A tiny world: three tables, one sentence pattern

Our model has only ever read queries from this small database. Every query has the same shape:

SELECT c1 FROM t WHERE c2 = v;

  • c1 and c2 are columns of table t.
  • c2 is never the same column as c1.
  • v is a digit from 1 to 9.

These rules allow exactly 270 different queries. Nobody gives the model these rules. It sees example queries and has to discover the rules itself.

A language model learns the structure of its data from examples alone. Our data is small enough that we can check exactly what it learned.

Pass 1 · The whole loopoverview

Pass 1: the model as a black box

So far our query is just text. In this pass we treat the model as a black box: what goes in, what comes out, how text gets generated, and what training changes.

We will not look inside the model yet. That is Pass 2.

Pass 1 · The whole loop1 of 4

An LLM does one thing: predict the next token

Give the model the beginning of a query. It returns a probability for each of the 113 tokens it knows. That is the entire interface.

Step through our query. Some next tokens are certain: after SELECT name FROM the model puts 1.000 on users, the only table with a name column.

Others are uncertain because the data is: after WHERE three columns are allowed, and after = any of nine digits.

A language model maps a prefix to a probability distribution over the next token. Everything else is built on top of that.

Pass 1 · The whole loop2 of 4

Writing text is the same prediction, in a loop

To generate, pick one token from the predicted distribution, append it, and feed the longer prefix back in. Each new token costs one more pass through the model.

Temperature divides the model's raw scores before they become probabilities. Below 1 it sharpens the distribution toward the top token; above 1 it flattens it.

Across 2,000 samples, 99.7% of queries follow the grammar at temperature 1, 90.2% at 2, and 54.1% at 3. Always taking the single most likely token gives SELECT id FROM products WHERE title = 3;

Text generation is a loop around next-token prediction. Temperature trades variety for correctness.

Pass 1 · The whole loop3 of 4

Training: make the right next token more likely

Our one query is eight training examples: each prefix, paired with the token that actually came next.

The model is scored with cross-entropy loss: the negative log of the probability it gave the true next token. A sure, correct guess costs 0. A guess of 0.01 costs 4.6.

loss=−ln⁡p(true next token)

An untrained model spreads probability evenly: about 1/113 per token, so each example costs about ln 113 = 4.73. Training adjusts all 9,968 parameters to push that number down.

Training means nudging the parameters so the tokens that really come next get higher probability.

Pass 1 · The whole loop4 of 4

Everything in this field is part of two loops

Training repeats: read a batch of text, predict every next token, measure the loss, compute how each parameter should change, update the parameters.

Inference repeats: run the model on the prompt, sample a token, append it, run again.

Each box below is a topic in its own right, and each one gets opened later in this deck. Select a box to jump to it.

Tokenizers, kernels, parallelism, serving systems and post-training are all ways of making one of these two loops better, faster, or bigger.

Pass 2 · Inside the model1 of 14

Tokenization: from 36 characters to 9 tokens

The model reads tokens from a fixed vocabulary. Byte-pair encoding (BPE) builds that vocabulary from data.

Start with single characters. Count every pair of neighbors in the corpus, merge the most frequent pair into a new token, and repeat. Our tokenizer made 74 merges over 2,000 queries.

Text is first split into words, each keeping its leading space, and merges never cross a word boundary. Ours stops at 74 merges because by then every word in its corpus is a single token. Production tokenizers stop at a chosen vocabulary size.

Keywords merge first because every query contains them. Then come pieces shared by several words: er (in users, orders, user_id) and id (in id, user_id).

Byte-level tokenizers, such as GPT-2's and Llama 3's, start from all 256 byte values, so any text can be encoded. Ours only knows the 39 characters in its corpus. Llama 3's vocabulary has 128,256 tokens.

BPE merges frequent neighbors until common strings are single tokens. Fewer tokens per text means less compute per text.

Pass 2 · Inside the model2 of 14

Each token id selects a row of numbers

The first layer is a table with one row of 16 numbers for each of the 113 tokens. Token id 63, users, selects row 63. Nothing else happens.

A second table holds one row per position. Its row is added, so users in position 3 enters the model differently than it would in position 6.

The model reads the first 8 tokens of our query. The 9th, ;, is never an input, only something to predict.

The table entries are parameters, learned like all others. Training placed the nine digits almost on top of each other: in this grammar they are interchangeable.

Llama 3 8B's token table is 128,256 rows × 4,096 columns: 525 million numbers.

The model never sees text. It sees one learned vector per token, plus one per position.

Pass 2 · Inside the model3 of 14

To predict, a position has to look back

The vector at FROM is the same in every query, so on its own it cannot know which table comes next. The answer depends on an earlier token: name means users, total means orders.

At WHERE the model needs two earlier facts: the table, which says which columns exist, and the selected column, which the rules exclude.

Edit the query and watch the predictions follow the earlier tokens. Try combinations that never occur in the data, too.

Each prediction depends on specific earlier tokens. The mechanism that fetches them is attention.

Pass 2 · Inside the model4 of 14

Attention, step 1: compare a query with every key

Attention runs as several independent heads; our model has 2 heads in each of its 2 layers. In each head, every position's vector (after RMSNorm) is multiplied by three learned matrices, giving a query q, a key k and a value v of 8 numbers each. This query is a vector, unrelated to our SQL query.

To decide where position i should look, the head takes the dot product of its query with the key of every position up to i, divided by √8. A large score means that position is relevant.

sij=qi·kj8withq=x^WQ,k=x^WKx̂: the position's vector after RMSNorm

Below: layer 1, head 2, asking from WHERE. The key of users matches its query far better than any other.

The query says what a position is looking for; the keys say what each earlier position offers. Their dot product is the match score.

Pass 2 · Inside the model5 of 14

Attention, step 2: scores become weights, weights mix values

Softmax turns the scores into weights that are positive and sum to 1. Each position may look at itself and earlier positions, never later ones. In training, all 8 predictions are computed in one pass, and this mask stops each position from seeing the token it must predict.

The head's output is the weighted sum of the value vectors. At WHERE, layer 1 head 2 puts 1.00 on users, so its output is essentially the value vector of users: the table's identity, copied to where it is needed.

Each head outputs 8 numbers. The 2 heads' outputs are placed side by side, 16 numbers, and multiplied by an output matrix WO before being added to the stream.

aij=esij∑m≤iesimouti=∑j≤iaijvj

Attention is a learned, content-based lookup: compare, normalize, mix.

Pass 2 · Inside the model6 of 14

Different heads learn different jobs

Our model has 2 layers with 2 heads each. Nobody assigned them roles. Training did.

At WHERE, layer 1 head 1 looks at name (0.98) and head 2 looks at users (1.00): the column to exclude, and the table whose columns are allowed. At FROM, layer 2 head 2 looks back at name (0.95) to choose the table.

Change the query. The same heads do the same jobs, because every query has the same shape. Rows are the positions asking; columns are the positions they look at.

Heads specialize. In our model one head finds the table and another finds the column already used.

Pass 2 · Inside the model7 of 14

Blocks add to a running sum, the residual stream

Each position carries one vector through the whole model. Every sublayer reads that vector, computes something, and adds its result back.

Attention moves information between positions. The MLP (multilayer perceptron) transforms each position on its own: 16 numbers to 64, a nonlinearity called GELU, then back to 16. RMSNorm rescales the copy each sublayer reads, so every sublayer sees inputs of a steady size even as the stream itself grows. Watch the size column.

x←x+Attn(norm(x))x←x+MLP(norm(x))

Our model stacks 2 blocks. Llama 3 70B stacks 80.

Blocks add to the vector instead of replacing it. That keeps information, and gradients, flowing through deep stacks.

Pass 2 · Inside the model8 of 14

The last vector becomes a score for every token

The final 16 numbers at a position, after one last RMSNorm, are multiplied by a 16 × 113 matrix: one score, a logit, for each token. Softmax turns logits into probabilities by exponentiating and dividing by the total.

pi=ezi/T∑jezj/T

Decoding settings act here. Temperature T divides the logits. Top-k keeps the k most likely tokens. Top-p keeps the smallest set of top tokens whose probabilities add up to at least p. Everything else gets probability 0, and the kept tokens are rescaled to sum to 1.

Logits are scores, softmax makes them probabilities, and temperature, top-k and top-p reshape them before a token is drawn.

Pass 2 · Inside the model9 of 14

The loss has a floor, and it isn't zero

After =, all nine digits are equally likely in the data. Probabilities must sum to 1, so a model can't give every digit more than 1/9. Averaged over the data, the loss after = can't drop below ln 9 = 2.197.

That floor is the entropy of the data. For our grammar we can compute it exactly at every position. Averaged over the data, with each of the 270 queries weighted by how often it occurs, it is 0.6937. Our trained model reaches 0.6942.

Perplexity is e raised to the loss. A perplexity of 9 after = means the model is choosing among 9 equally likely options, which is exactly the situation.

On a single query a model can land on either side of the ideal value. Only the average over the data has a floor. Loss is measured in nats because it uses the natural logarithm.

The floor is the data's own uncertainty. The gap between the loss and the floor is what the model still has to learn. Scaling laws call this floor the irreducible loss.

Pass 2 · Inside the model10 of 14

The gradient says which way to move each number

For softmax followed by cross-entropy, the gradient of the loss with respect to each logit is simply p − y: the predicted probability, minus 1 for the true token and minus 0 for all others.

∂loss∂zi=pi−yi

Gradient descent subtracts learning rate × gradient. So each step raises the true token's logit by lr × (1 − p) and lowers every other logit by lr × that token's own p.

Here we run that update by hand on four logits: the scores for id, name, email and age after …users WHERE. Each step draws the true next token from the real data, where name never occurs. With a small learning rate the probabilities settle near 1/3, 0, 1/3, 1/3. With a large one they chase whichever token was drawn last.

Gradient descent: compute the gradient, take a small step against it, repeat.

Pass 2 · Inside the model11 of 14

Backpropagation: the chain rule, run backwards

The gradient of a logit is easy. A parameter deep inside the model affects the loss through a chain of operations, and its gradient adds up, over every path from the parameter to the loss, the product of the local derivatives along that path.

Frameworks record every operation of the forward pass. The backward pass visits them in reverse order, multiplying by each local derivative. One forward and one backward pass yield the gradient of all 9,968 parameters.

The backward pass costs about twice the forward pass, so a training step costs about 3× a forward pass. That factor is where the 6 in “6 × parameters × tokens” comes from (Pass 3).

Autograd turns any differentiable computation into gradients for every parameter, at about three times the cost of just running it.

Pass 2 · Inside the model12 of 14

Optimizers decide how big each step is

Plain gradient descent (SGD) uses one learning rate for every parameter. The steepest direction caps that rate: on this bowl, above 0.08 the steep coordinate blows up. At 0.07 the flat coordinate closes only 7% of its remaining distance per step.

Adam divides each parameter's step by a running estimate of that parameter's gradient size. Steep and flat coordinates move at a similar pace; from this start, equally far along both axes, its path runs along the diagonal. It also averages recent gradients (momentum). AdamW applies weight decay as a separate step.

Our model trained with Adam: peak rate 0.01, β₁ = 0.9, β₂ = 0.95 (how quickly its two running averages forget). It used PyTorch's AdamW with weight decay 0, which is the same thing. The rate warms up over 100 steps, because the first updates rely on statistics from only a few batches. Then it decays: mini-batch gradients are noisy, and a smaller rate late in training lets the loss settle lower.

Adam adapts each parameter's step size to its own gradient history. Adam(W) with warmup and decay is the standard recipe for training transformers.

These are the real training curves of our model. Drag through training and the whole model, weights and all, is swapped for its saved state at that step.

The fixed tokens (FROM, WHERE, =, ;) cost almost nothing by step 100. The table after FROM follows by step 150, once a head learns to look back at the selected column. The column after WHERE needs two lookups and converges last.

Simple rules are learned first. Rules that need attention to the right earlier token come later.

Pass 2 · Inside the model14 of 15

Did it learn the rules, or memorize the data?

Our model saw each of the 270 queries about 2,800 times. To see what it really learned, we trained a second copy with the same recipe on only 243 of them. The other 27, including our query, were held out: it never saw them.

On the held-out queries it still gets the structure right: the table after the column, the filter column after the table. Those are rules, and rules carry over to new queries.

The digit is different. In its training data our query's start was followed by every digit except 7, and the model learned exactly that: it gives 7 a probability of 0.003. Its loss after = on held-out queries is 6.76, against ln 9 = 2.20 for a model that knows digits are random.

On the queries it did see, its loss after = is 2.10, below the true floor of 2.197. Beating the floor is the signature of memorization: the model is fitting its particular sample, not the language. Only held-out data shows it.

Real models are judged the same way: on held-out text and on benchmarks they never trained on. When benchmark questions leak into the training data, a problem called contamination, the scores overstate the model.

Training loss can't tell learning from memorizing. Loss on held-out data can.

Pass 2 · Inside the model14 of 14

Same recipe, scaled up

Production models use the same parts: token and position information, attention, MLPs, residual stream, softmax over a vocabulary. They have far more of each, plus a few upgrades.

  • RoPE encodes position by rotating q and k, instead of adding a position vector.
  • SwiGLU MLPs use a gated activation in place of GELU.
  • Grouped-query attention lets many query heads share a few key/value heads: Llama 3 70B has 64 query heads but 8 KV heads.
  • Mixture of experts routes each token to a few of many MLPs: DeepSeek-V3 has 671B parameters, 37B active per token.

Going from ten thousand to hundreds of billions of parameters is mostly more layers, wider vectors, more heads, and far more data.

Pass 3 · Training at scaleoverview

Pass 3: the same recipe, 40 million times larger

We know every step of our 9,968-parameter model. A 405-billion-parameter model runs the same steps. What changes is how much work there is, where it runs, and what breaks along the way.

This pass is about compute, memory, communication and reliability.

Pass 3 · Training at scale1 of 13

Counting the work: 6 × parameters × tokens

A forward pass does about 2 floating-point operations per parameter per token: one multiply and one add. The backward pass costs about twice as much. So training costs about 6 FLOPs per parameter per token.

C≈6·N·DC: training FLOPs · N: parameters · D: training tokens

Our model: 6 × 9,968 × 6,144,000 ≈ 3.7 × 10¹¹ FLOPs, a few seconds of laptop time. Llama 3.1 405B: 6 × 405 × 10⁹ × 15.6 × 10¹² ≈ 3.8 × 10²⁵ FLOPs, the figure Meta reports.

Dividing by what the hardware sustains gives time. An H100 peaks at 989 TFLOP/s in dense BF16. Large runs sustain about 40% of peak, a ratio called model FLOPs utilization (MFU).

6ND leaves out attention's own work over the context: about 4% extra for the 405B model at 8,192 tokens, far more at 128K.

Training compute is predictable from parameters and tokens. Utilization decides how long it takes.

Pass 3 · Training at scale2 of 13

Scaling laws: how big, and for how long

For a fixed budget C ≈ 6ND you can train a bigger model on fewer tokens, or a smaller one on more. Loss falls as a smooth power law in both, so the best split can be predicted from small experiments.

DeepMind's Chinchilla study found the compute-optimal split is roughly 20 tokens per parameter. Chinchilla itself is 70B parameters trained on 1.4T tokens. Meta's own fits for Llama 3 favored more data: 402B parameters on 16.55T tokens for 3.8 × 10²⁵ FLOPs, about 41 tokens per parameter. They trained 405B on 15.6T. The best ratio depends on the data and the fitting method; 20 is a rule of thumb.

Smaller models are often trained far past that point. Llama 3.1 8B saw about 15T tokens, roughly 1,900 per parameter, because a smaller model is cheaper to serve and serving costs are paid on every request.

Loss curves also flatten toward a floor: the irreducible part, which we computed exactly for our grammar in Pass 2.

Scaling laws turn “how big should the model be?” into arithmetic. Small models are deliberately over-trained to make inference cheap.

Pass 3 · Training at scale3 of 13

Pretraining data: most of the work is cleaning

Real pretraining corpora start as web crawls: billions of HTML pages. A pipeline turns them into tokens. It extracts the text, identifies the language, filters for quality and safety, removes duplicates and personal data, mixes sources, tokenizes, and shards.

Duplicates waste compute and are more likely to be memorized. Exact copies are caught by hashing. Near-copies need a similarity measure. MinHash compresses each document's set of word sequences into a short signature whose overlap estimates their Jaccard similarity: shared sequences divided by all distinct sequences. Locality-sensitive hashing then buckets the signatures so that only documents in the same bucket get compared.

Our own corpus is almost all duplicates: the 2,000 queries used to build the tokenizer contain only 269 distinct ones.

Data quality is engineered. Filtering and deduplicating trillions of tokens is a large data-infrastructure problem.

Pass 3 · Training at scale4 of 13

Why a 70B model doesn't fit on one GPU

Training with Adam in mixed precision keeps about 16 bytes per parameter: the BF16 weights (2) and gradients (2), plus, in FP32, a master copy of the weights (4) and Adam's two running averages (4 + 4).

For 70B parameters that is 1.12 TB before a single activation is stored. One H100 holds 80 GB. Even the BF16 weights alone, 140 GB, don't fit.

Activations, the intermediate values kept for the backward pass, add more and grow with batch size and sequence length. They can be cut by recomputing them during the backward pass, which is called activation checkpointing.

Recipes vary: Llama 3 accumulates and reduce-scatters gradients in FP32, which adds 2 bytes per parameter. Our model trains in FP32: 4 bytes each for weights, gradients and both Adam averages. That is also 16 bytes per parameter, 159 KB in total.

Model state alone needs about 16 bytes per parameter, so large models must be split across GPUs. The next slides show how.

Pass 3 · Training at scale5 of 13

A GPU is fast at math and slower at memory

An H100 SXM can do 989 trillion BF16 operations per second (dense) but read only 3.35 TB per second from its 80 GB of high-bandwidth memory (HBM), the GPU's main memory. That is about 295 operations for every byte read.

Arithmetic intensity is operations per byte moved. For matrix multiplies on the tensor cores, the GPU's matrix units, an intensity below about 295 means the operation is memory-bound and the math units wait for data. Large matrix multiplies are compute-bound. Elementwise operations such as additions, GELU and normalization run on the ordinary CUDA cores (67 TFLOP/s in FP32, a threshold near 20) and do only a few operations per byte, so they are memory-bound too.

Multiplying B token vectors by a d × d BF16 weight matrix does 2Bd² operations and moves about 2d² bytes of weights, so its intensity is roughly B. Generating one token at a time (B = 1) leaves most of the GPU idle.

NVIDIA's datasheet lists 1,979 TFLOP/s BF16, a figure that assumes 2:4 structured sparsity. Dense math gets half.

Most performance work is feeding the math units: larger batches, fused kernels, fewer trips to memory.

Pass 3 · Training at scale6 of 13

FlashAttention: the same math, fewer trips to memory

Standard attention writes the full n × n score matrix to GPU memory, reads it back for the softmax, writes the weights, then reads them again. At 8,192 tokens that is 67 million scores per head, 128 MiB in BF16, moving through HBM several times.

FlashAttention processes keys and values in tiles small enough for fast on-chip memory and never stores the score matrix. The key step is an online softmax: keep a running maximum m, a running sum ℓ and a running output o, and rescale them whenever a new tile raises the maximum.

Step through it on our model's real scores: layer 1, head 2, asking from WHERE, keys in tiles of 2. The result matches the full softmax exactly.

FlashAttention is exact attention. It is faster because it moves less data, not because it does less math.

Pass 3 · Training at scale7 of 13

Fewer bits per number: FP32, BF16, FP16, FP8

A floating-point number spends its bits on a sign, an exponent, which sets the range, and a mantissa, which sets the precision. Smaller formats halve or quarter memory and traffic, and the GPU's matrix units (tensor cores) run faster on them.

BF16 keeps FP32's 8 exponent bits: same range, less precision. It rarely overflows, which made it the default for training. FP16 has more precision but far less range, so training in it needs loss scaling to keep small gradients from rounding to zero. FP8 needs a scale factor per tensor or per block.

Try a value from our model, a tiny gradient, or a large activation.

Precision is a budget. Spend bits on range or on detail, and add scaling where the budget runs out.

Pass 3 · Training at scale8 of 13

Data parallelism: different queries per GPU, one shared update

Give each of N GPUs a full copy of the model and a different slice of the batch. Each computes gradients on its own queries. Before the update, an all-reduce adds up the gradients from all GPUs and every copy divides by N, so all copies take the same averaged step.

Ring all-reduce splits the gradient into N chunks. For N − 1 steps each GPU sends a chunk to its neighbor and adds the chunk it receives (reduce-scatter). For N − 1 more steps the finished chunks travel around the ring (all-gather). Each GPU sends 2(N − 1)/N times the gradient size, almost independent of N.

T≈2(N−1)α+2(N−1)N·Sβα: per-step latency · S: gradient bytes · β: link bandwidth

The ring pays latency 2(N − 1) times. Tree and recursive-doubling algorithms need only about 2 log₂N latency steps, so communication libraries such as NVIDIA's NCCL pick algorithms by message size and topology.

Data parallelism scales because ring all-reduce traffic per GPU stays near twice the gradient size however many GPUs join. What grows with N is the latency term, and beyond one server the links are slower.

Pass 3 · Training at scale9 of 13

Sharding the model state: ZeRO and FSDP

Plain data parallelism keeps all 16 bytes per parameter on every GPU. ZeRO removes that redundancy in stages: shard the optimizer state across the N data-parallel GPUs (stage 1), then the gradients (stage 2), then the weights themselves (stage 3, which PyTorch calls FSDP).

Stage 3 gathers each layer's weights just before using them and frees them afterwards. Gradients are reduce-scattered instead of all-reduced. The ZeRO paper puts the communication at 1.5× that of plain data parallelism, in exchange for an N-fold cut in memory.

With full sharding, 70B parameters of model state fit on 64 GPUs at 17.5 GB each.

Pass 3 · Training at scale10 of 13

Tensor parallelism: split every matrix

When one layer is too big or too slow for one GPU, split its matrices. NVIDIA's Megatron-LM training library splits the MLP's first matrix by columns and the second by rows. Each GPU computes a share of the hidden units and a partial output, and one all-reduce adds the partial outputs.

Below, our model's real layer-1 MLP at WHERE runs on two or four simulated GPUs. Their partial results add up to the single-GPU output, to rounding error.

Attention is split the same way, by heads: each GPU runs some of the heads and multiplies by its rows of WO, and a second all-reduce sums the results.

This costs two all-reduces per layer in the forward pass and two in the backward pass, so tensor parallelism stays inside one server, where H100s are connected by NVLink at 900 GB/s (450 GB/s in each direction).

Tensor parallelism splits each layer across GPUs and pays with frequent communication, so it runs on the fastest links.

Pass 3 · Training at scale11 of 13

Pipeline parallelism: split the layers, mind the bubble

Pipeline parallelism gives each GPU a contiguous range of layers. The batch is cut into micro-batches: stage 1 starts micro-batch 2 while stage 2 is still working on micro-batch 1.

At the start and end of each batch some stages sit idle: the bubble. With p stages and m micro-batches, the idle share of the pipeline's time is (p − 1)/(m + p − 1). Megatron-LM writes the same overhead as (p − 1)/m of the ideal compute time.

The 1F1B schedule alternates one forward and one backward per micro-batch once the pipeline is full. The bubble is the same, but each stage holds activations for at most p micro-batches instead of m.

Pipelines cut per-GPU memory by layers and communicate only between neighboring stages. More micro-batches shrink the bubble.

Pass 3 · Training at scale12 of 14

Mixture of experts: more parameters, same work per token

A mixture-of-experts (MoE) layer replaces one MLP with many expert MLPs and a small router. For each token, the router scores the experts and sends the token to its top k. Parameters grow with the number of experts; the work per token grows only with k. DeepSeek-V3 has 671B parameters, of which 37B are used for each token.

In large runs, experts live on different GPUs: expert parallelism. Every MoE layer then needs two all-to-all exchanges: one sends each token to its experts' GPUs, the other brings the results back.

If the router favors a few experts, their GPUs become the bottleneck while the others wait. Some systems cap how many tokens an expert accepts per batch and drop the overflow. Training also pushes the router toward balance, with an extra loss term or with per-expert bias terms adjusted during training, which DeepSeek-V3 relies on.

MoE buys parameters without more work per token, and pays in all-to-all traffic and load balancing.

Pass 3 · Training at scale12 of 13

All together: Llama 3.1 405B on 16,384 GPUs

Real runs combine these methods. Meta trained Llama 3.1 405B (described in its paper The Llama 3 Herd of Models) with tensor parallelism of 8 inside each server, pipeline parallelism of 16 across servers, and fully sharded data parallelism of 128 across pipelines: 8 × 16 × 128 = 16,384 GPUs.

The layout puts the most frequent communication on the fastest links: tensor parallelism on NVLink inside a server, pipeline traffic between neighboring stages, and data-parallel gradient reduction across the whole cluster. For 128K-token sequences they added context parallelism of 16.

Meta reports 400 TFLOP/s per GPU at this scale, 41% MFU; 43% on 8,192 GPUs; and 38% during long-context training.

At scale, the parallelism layout is chosen so the most frequent communication uses the fastest links.

Pass 3 · Training at scale13 of 13

At this scale, something is always failing

Over a 54-day stretch of the Llama 3.1 405B pretraining run, Meta counted 466 job interruptions: 47 planned and 419 unexpected. About 78% of the unexpected ones were attributed to confirmed or suspected hardware issues. The run still achieved over 90% effective training time.

That is one unexpected stop about every 3 hours. Each stop loses the work done since the last checkpoint, plus restart time. Checkpointing too often wastes time writing; too rarely wastes time redoing work.

A classic first-order rule (Young, 1974): checkpoint every √(2 × C × M), where C is the time to write a checkpoint and M is the mean time between failures.

Reliability is part of training. Fast checkpoints, quick failure detection and automatic restarts are worth whole percentage points of a huge cluster.

Pass 4 · Servingoverview

Pass 4: answering requests

Training is done. Now our query arrives as a request from a user, together with thousands of others, and the model has to answer quickly and cheaply.

Serving has different bottlenecks from training. Most of this pass is about memory bandwidth.

Pass 4 · Serving1 of 9

A request arrives: prefill, then decode

A user sends the prompt SELECT name FROM. The server first runs the model once over all 3 prompt tokens together. This prefill produces the first new token. Then it decodes: one forward pass per additional token, each feeding in only the newest token.

With a prompt of hundreds of tokens or more, prefill processes many tokens per pass and is compute-bound; our 3-token prompt is too short for that. Decode processes one token per request per pass, so it is limited by memory bandwidth. Users feel two numbers: time to first token (TTFT), mostly prefill, and time per output token (TPOT), set by decode.

Serving has two very different phases: one parallel prefill, then a sequential decode.

Pass 4 · Serving2 of 9

The KV cache: never recompute the past

In every decode step, attention needs the keys and values of all earlier tokens. Those never change, because a token can't see the future. So the server computes each token's keys and values once and keeps them: the KV cache.

Without the cache, producing token n recomputes keys and values for all n tokens, so total work grows with n². With it, each step computes them only for the newest token.

Each row below is one token's entry: a key and a value for each of the 2 heads in each of the 2 layers, 64 numbers in all. The logits come out identical either way; the slide checks this live.

The KV cache trades memory for compute: no decode step recomputes the past. What still grows with the sequence is attention's reading of the cache.

Pass 4 · Serving3 of 9

How big the KV cache gets

bytes per token=2·L·hkv·dhead·b2: a key and a value · L: layers · hkv: key/value heads · dhead: numbers per head · b: bytes per number

Our model in FP32: 2 × 2 × 2 × 8 × 4 = 256 bytes per token. Llama 3.1 70B in BF16: 2 × 80 × 8 × 128 × 2 = 327,680 bytes, or 320 KiB per token. An 8,192-token conversation needs 2.5 GiB; 64 of them at once need 160 GiB.

Grouped-query attention is why that figure isn't 8× larger. If all 64 query heads kept their own keys and values, the same conversation would need 20 GiB.

KV sizes here use binary units (1 GiB = 1.074 GB); GPU memory is quoted in decimal GB.

KV memory grows with layers × context × users. It, more than the weights, often limits how many users a GPU can serve.

Pass 4 · Serving4 of 9

Decode is memory-bound, so batch it

Each decode step reads every weight once. For Llama 3.1 70B in BF16 that is 140 GB per step. On 8 H100s reading 26.8 TB/s together, a step takes at least 5.2 ms, however little math it does.

Batching B requests lets one read of the weights serve B tokens. Until the math units become the bottleneck, the step barely slows, so total throughput grows almost B-fold while each user's speed stays the same.

Each request also reads its own KV cache every step, so long contexts eat into the gain.

At small batch sizes, decode speed is set by memory bandwidth. Batching is how servers turn bandwidth into throughput.

Pass 4 · Serving5 of 9

Continuous batching: refill the batch every step

Requests finish at different times: one query needs 2 more tokens, another 8. With static batching, a batch runs until its longest request finishes, and finished requests' slots sit empty.

Continuous batching schedules at every decode step: finished requests leave and waiting ones join immediately. The Orca paper introduced this as iteration-level scheduling. vLLM, SGLang and TensorRT-LLM all work this way.

New requests also need a prefill, which competes with the decode steps of requests already running. Engines split long prompts into chunks so decode keeps moving (chunked prefill); disaggregation, two slides on, separates the two entirely.

Scheduling per step instead of per batch keeps the GPU full and cuts waiting time.

Pass 4 · Serving6 of 9

PagedAttention: KV memory in fixed-size blocks

Reserving one contiguous KV region per request, sized for the longest allowed output, wastes memory: most requests end early. The vLLM paper measured that existing systems used only 20–38% of their KV memory for actual tokens.

vLLM stores each request's cache in fixed-size blocks, using the same paging technique operating systems use for virtual memory, with a block table per request. Blocks are allocated as tokens arrive and freed when a request finishes. The paper reports 96% of KV memory holding actual tokens.

Blocks also make sharing easy: requests that start with the same prompt can point at the same physical blocks. That is prefix caching.

Paging the KV cache removes fragmentation and lets requests share prefixes, so more requests fit on each GPU.

Pass 4 · Serving7 of 9

Speculative decoding: guess ahead, verify in one pass

Because decode is memory-bound, one pass over 5 tokens costs about as much as a pass over 1. A small draft model proposes k tokens. The large model scores all of them in one pass. The server keeps the longest run it accepts, plus one token from the large model itself.

Each draft token is accepted with probability min(1, p/q), where p and q are the large and draft models' probabilities for it. On a rejection, a replacement is drawn from what is left of p. This makes the output distribution exactly the large model's.

E[tokens per large-model pass]=1−αk+11−αα: chance each draft token is accepted · k: draft length

Below, the draft is our own model saved at training step 150, and the large model is the final one. Acceptance depends on how similar their distributions are, not on how certain: both spread the digit evenly, so 93% of drafted digits are accepted, while the still-unsure column after WHERE is accepted only 67% of the time.

Speculative decoding spends spare compute to cut the number of slow decode passes, without changing what the model outputs.

Pass 4 · Serving8 of 9

Quantization: fewer bits per weight

Weights can be stored as 8- or 4-bit integers instead of 16-bit floats. Each group of weights gets a scale s so that its largest weight maps to the largest integer, and every weight is rounded to the nearest step.

q=round(w/s),s=max|w|2b−1−1,w≈s·q

Decode reads every weight each step, so halving the bytes nearly halves the time per token. Llama 3.1 70B weighs 140 GB in BF16, 70 GB in 8 bits, 35 GB in 4 bits.

Below, our whole model is quantized live and evaluated over all 270 queries. With one scale per output channel, 8, 6 and 5 bits barely move the loss. At 4 bits it breaks: users after FROM falls from 1.000 to 0.000.

Large models usually tolerate 4-bit weights well, using one scale per small group of weights and methods such as GPTQ, which picks roundings that minimize each layer's output error, and AWQ, which scales up the channels that matter most to the activations before rounding. A model with 16-number vectors has no slack.

Quantization trades a little accuracy for a lot of memory and speed. Measure the loss; don't assume it.

Pass 4 · Serving9 of 9

Serving at scale: place work by its bottleneck

A large deployment runs many copies of the model. A router sends each request to a replica. Inside a replica, tensor parallelism spreads each layer over the GPUs of a server.

Because prefill is compute-bound and decode is bandwidth-bound, some systems run them on separate GPU pools and ship the KV cache from one to the other over the network with RDMA, direct memory-to-memory transfers. This is prefill/decode disaggregation. Routers also prefer a replica that already holds a request's prefix in its cache.

Teams track goodput: requests per second that meet the latency targets for both time to first token and time per output token.

At fleet scale, serving is distributed scheduling: route, batch, cache, and place each phase where its bottleneck is cheapest.

Supervised fine-tuning: same loss, chosen examples

A pretrained model continues text. To make it answer requests, it is trained further on example conversations, written by people or generated by models and filtered for quality.

Each conversation is flattened into one token sequence, with special marker tokens around each turn: the chat template. The loss is the same next-token cross-entropy as before, but only on the assistant's tokens. The model reads the user's message without being trained to predict it.

Preference training: which answer is better?

Many qualities are easier to compare than to write down. A labeler, or a model following written principles, sees two answers to the same prompt and picks the better one.

In RLHF, a reward model learns to score answers so that the preferred one scores higher: P(A preferred over B) = σ(rA − rB). The language model is then trained with reinforcement learning, sampling answers and making the high-scoring ones more likely, with a penalty for drifting far from where it started.

DPO skips the reward model. It widens the gap between the preferred and the rejected answer, each scored relative to a frozen reference copy of the model. Below, π is the model being trained, πref the frozen copy, and σ the logistic function 1/(1 + e−x).

LDPO=−logσ(β[logπ(yw)πref(yw)−logπ(yl)πref(yl)])yw: preferred answer · yl: rejected answer · β: strength of the pull toward the reference (larger β keeps the model closer)

Anthropic's Constitutional AI has an AI model, guided by a written set of principles, produce much of this feedback (RLAIF).

Preference training turns “A is better than B” into a gradient, through a reward model (RLHF) or directly (DPO).

Pass 5 · Becoming an assistant3 of 4

Reinforcement learning with answers you can check

For SQL, math or code, an answer can be checked by a program. Run the query on the database: reward 1 if it returns the right rows, 0 if not. No person has to grade it.

GRPO (from DeepSeekMath) samples a group of answers to the same prompt and gives each one the advantage (reward − group mean) / group standard deviation. Better-than-average answers become more likely under the policy, the model's probabilities over answers, and worse ones less likely, with no separate critic, a second network that predicts how good an answer will be.

The task: return the email of user 7. Our model continues from SELECT email FROM users WHERE and must pick a column and a value. Only id = 7 returns the right row: about 1 sample in 26 for the starting model.

If every answer in a group gets the same reward, all advantages are 0 and the group teaches nothing. Watch the groups with no ✓.

To run in your browser, this demo updates only the two output distributions the task depends on, the column and the digit. It also leaves out GRPO's clipping and its penalty for drifting from the reference model. A full run updates every parameter through backpropagation.

With a verifier, a model improves by trial and error. GRPO compares answers within a group instead of training a separate critic.

Pass 5 · Becoming an assistant4 of 4

The RL loop is a distributed system

In large-scale RL, generating answers takes most of the time. So the loop runs an inference engine and a training job side by side.

  1. Rollout workers run an inference engine such as vLLM or SGLang and sample groups of answers.
  2. Verifiers score them: run the SQL in a sandbox, check the math, run the unit tests.
  3. The trainer computes advantages and updates the weights, sharded with FSDP or Megatron.
  4. Weight sync sends the new weights back to the rollout workers.

Long answers make rollouts slow and uneven, so systems overlap generation with training, accept slightly stale samples, and rebalance work across GPUs. Open-source examples include veRL (from ByteDance, built on Ray), OpenRLHF and TRL.

Modern post-training couples a serving system and a training system in one loop. Scheduling them well is an infrastructure problem.
